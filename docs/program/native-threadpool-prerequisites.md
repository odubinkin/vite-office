# Native thread-pool task and no-worker prerequisites

The original `comphelper::ThreadTask`, task-tag counter and explicit `ThreadPool(0)` queue now exist at the source/header ownership boundaries. The no-worker constructor is a real upstream profile tested by `ThreadPoolTest::testNoThreads`; it is not installed as the shared optimal pool or selected for large ZIP writes. Positive-count construction retains the original maximum, but attempted worker launch fails explicitly until the real worker backend exists.

The implementation retains front insertion/back removal FIFO ordering, tag counts, queue-wide work while waiting for one tag, completed-tag early return, unrelated queued tasks surviving a partial wait, optional joining, explicit no-worker shutdown and virtual task destruction. Actual linked native std::mutex guards the source scopes. The Emscripten default `bJoin=false` is preserved. The original signed32 getWorkerCount return narrows the wasm32 unsigned worker limit. Worker-vector/thread IDs, shared_ptr machine-level representation, atomic/thread contention and pending condition-variable waiting remain unqualified.

The original no-thread QA call sequence of eight tasks is ported over the actual abstract task extension point. Browser fixtures observe the actual calling realm rather than inventing native thread identifiers. Assertions and work results are inspected outside task callbacks because the source exec deliberately catches work exceptions. Further tests exercise real ZIP compression, FIFO/tag completion, destruction, exceptions and unavailable worker/wait boundaries. Chromium main and DOM-free Worker each run actual package stream save/reopen tasks through the explicit no-worker pool.

WRITER627/CALC694 records that a no-worker task submitting work to the same pool can reacquire the already-held nonrecursive pool mutex. The original lock order is retained; tests do not execute a deliberate deadlock. Nothing here qualifies native concurrent scheduling or full document/ZIP thread integration.

Remaining work includes preferred concurrency/shared optimal construction, ThreadWorker launch/execution, real condition-variable waiting, background ZIP scheduling and parallel block compression. The background ZIP entry object/temp-buffer/task/error-retention work now exists (see `native-zip-background-task.md`), but is not installed as a serial replacement for production worker tasks. Pako supplies dictionary setup but does not export the deflateBound required by original ThreadedDeflater; that dependency is unresolved rather than replaced by an invented output-buffer heuristic. The production100000/1000000-byte branch thresholds remain unchanged and explicitly unported. Whole DOCX/XLSX package/filter/UI acceptance and the earlier full ZipPackage coverage gate remain unfinished.
